On 2026-08-08 an Acceptance Criteria document was produced (research/planning only, no code written) for a new `md-split-button` component: leading action button + trailing icon-button that opens a menu, per MD3 "Split buttons" (introduced in Material 3 Expressive). The AC was handed off to a frontend engineer agent to turn into an implementation plan.

Key findings from repo research that should inform any future implementation:

- The official m3.material.io/components/split-button pages are JS-rendered SPAs — WebFetch could not retrieve spec body text (only the page heading came through). Anatomy/behavior details in the AC were reconstructed from web search snippets + established MD3 button/menu conventions, not scraped verbatim from the spec. Re-verify exact spacing/motion tokens against the live site (or Figma MD3 kit) before finalizing visual implementation.
- **No menu/popover primitive exists anywhere in this repo yet.** `md-select` (`components/select/select.js`) uses a native `<select>` element for its dropdown, not a custom overlay. `md-dialog` uses native `<dialog>` (`showModal()`). There is no `role="menu"` / anchored-popover component to reuse. This is the biggest open decision for split-button implementation: build a scoped-internal menu just for split-button (MVP recommendation), or invest in a shared `md-menu` primitive first. See [[frontend_reusable_primitives]] if that memory exists, otherwise check current state of `components/` before assuming.
- Repo convention for composite/multi-part components is a _group + leaf_ pair (see `md-segmented-button-group` wrapping `md-segmented-button` in `components/segmented-button/`), with the group owning roving-tabindex keyboard nav, ARIA container role, and prop cascade (e.g. `disabled`) down to children via a `_syncSegmentProps`-style method called from `updated()`. The AC recommended split-button follow a similar internal-composition approach (single custom element internally composing a leading button + trailing icon-button + menu list, not necessarily separate public custom elements).
- `BaseButton` (`components/button/base-button.js`) is the shared base for all button-like components (`md-button`, `md-fab`, `md-icon-button`, `md-segmented-button`) providing `disabled`, `loading`, `href`, `type`, `form`, click/submit handling, and icon/text slot-content tracking (`hasIcon`, `childrenContent`, `slotHasContent`). Any new button-like leaf (leading segment, trailing segment) should extend or compose this rather than reinventing.
- `package.json` `exports` map is missing entries for `./segmented-button` and any menu-related export even though the component exists in `components/`. Worth flagging to the user if/when split-button ships, since new components have historically needed manual addition to the exports map (not automated).

**Why:** Captures the non-obvious research findings (spec page unreachable via WebFetch, no menu primitive exists) so the next agent picking up split-button implementation doesn't re-discover them from scratch.

**How to apply:** Before starting split-button implementation, re-check whether `components/menu/` or similar has been added since this memory was written (grep `components/` for `menu`), and re-verify MD3 spec details live rather than trusting the AC's reconstructed anatomy section verbatim.

**2026-08-09 follow-up (shape/corner-radius research):** Confirmed the WebFetch failure is not limited to `/overview` — `m3.material.io/components/split-button/specs`, `/components/button-groups/specs`, and even the general `/styles/shape/corner-radius-scale` page all return only the page heading via WebFetch (fully JS-rendered SPA, no static body content at all on m3.material.io). Do not keep retrying different m3.material.io URLs expecting different results — the whole site behaves this way for WebFetch.

- Useful secondary source found: Compose Multiplatform / AndroidX `SplitButtonDefaults` API docs (e.g. `kotlinlang.org/api/compose-multiplatform/material3/androidx.compose.material3/-split-button-defaults/`) confirm the _structure_ of MD3's split-button shape system even though literal dp values aren't rendered in fetched text: five size variants (`ExtraSmall/Small/Medium/Large/ExtraLarge` `ContainerHeight`), a single `OuterCornerSize` (implying outer corners stay one consistent — likely fully-rounded — shape across all sizes), and per-size `InnerCornerSize` **plus a separate `InnerCornerSizePressed`** — i.e. official confirmation that the seam-side (inner) corners do morph on press, while outer corners don't. This validates the AC's reconstructed "expressive morph on press" behavior structurally, but exact dp numbers for any of this remain unconfirmed — would need Android source (`SplitButtonTokens`/`Material3ExpressiveTokens` in the AndroidX Compose Material3 source repo) or direct Figma MD3 kit inspection, not WebFetch.
